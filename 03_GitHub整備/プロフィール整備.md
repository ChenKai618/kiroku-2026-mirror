### プロフィールREADMEを刷新（ビジュアル重心）

**最初の失敗**：一度「経歴を丁寧に書いた版」を作ったが、本人から
**「これは履歴書の二枚目になっている。GitHubのプロフィールは見た目と技術性を見せる場所だ」**
という指摘を受けた。**この指摘は正しい。**

職務経歴書は `02_書類/` にある。**プロフィールREADMEに同じものを置く意味はない。**
プロフィールの役割は「30秒で技術的な印象を残す」ことであって、経歴の再掲ではない。

**変更前の問題点**：
- 「目前在日本当社畜」← **自嘲。日本の採用側が見ると印象が悪い**
- **中国語** ← 日本の採用担当は読めない
- 内容がサイクリング・ランニング中心で、**技術情報がゼロ**

**採用したビジュアル要素**（全て稼働確認済み・15枚すべてHTTP 200）：

| 要素 | サービス | 役割 |
|---|---|---|
| **波形ヘッダー / フッター** | `capsule-render.vercel.app` | 上下を締める。グラデーション（紺→青） |
| **タイピングアニメーション** | `readme-typing-svg.demolab.com` | 3行を巡回表示。**動きがあるものは目を引く** |
| **資格バッジ（for-the-badge）** | `custom-icon-badges.demolab.com` | AWS公式ロゴ入り。SAP/SAA/CLF + JLPT N1 |
| **技術アイコン** | `skillicons.dev` | ★**これが本命**。文字のバッジではなく**実際のロゴ画像**が並ぶ |
| **言語構成グラフ** | `github-readme-stats` のミラー | 本家は503。**rickstaa のミラーは稼働している** |
| **Streak** | `github-readme-streak-stats.herokuapp.com` | 継続日数 |
| **yamlコードブロック** | — | 現在の案件を**設定ファイル風**に見せる。表よりコード寄りの印象になる |
| **2×2 テーブルレイアウト** | HTML `<table>` | プロジェクトをカード状に並べる |

**⚠️ 使わなかったサービス（動作しなかった）**：

| サービス | 状態 |
|---|---|
| `github-readme-stats.vercel.app`（本家） | **503** — 公式インスタンスが不安定 |
| `github-profile-trophy.vercel.app` | **402** — 課金要求 |
| `github-readme-activity-graph.vercel.app` | **402** — 同上 |

**壊れた画像がプロフィールに残る方が、その要素がない方より悪い。**
新しいサービスを追加するときは、**必ず `curl` でHTTPステータスを確認してから貼ること。**

**設計上の判断**：
- **技術アイコン（skillicons）を上部に大きく置いた** — 本人の要望。
  文字のバッジより**ロゴ画像の方が視覚的に強い**
- **現在の案件を yaml 風のコードブロックにした** — 散文で書くと履歴書になる。
  コードブロックにすると**エンジニアのプロフィールに見える**
- **ADRの中身をブロック引用で見せた** — リンクだけでは踏まれない。
  「GPUが1枚だから直列」「再生時刻を唯一の状態源に」という**判断そのもの**を読ませる
- **草（contribution graph）を主役にしない** — 実装の多くはAI併用であり、
  コミット数を実装力の証拠として提示しない（[ADR-0006](../docs/adr/0006-ai-assisted-development-disclosure.md)）
- **経歴の羅列を削除した** — それは職務経歴書の仕事

### 🎯 このプロフィールが面接で機能する仕組み

面接官が「個人開発について教えてください」と聞く前に、
**プロフィールを見た時点で以下が伝わっている**：

1. 金融系基幹システムのクラウド移行に従事している（＝業務の格）
2. AWS SAP を持っている（＝保有者が少ない）

**3と4が主武器。** 実装力ではなく設計判断で差別化する構造
（[ADR-0005](../docs/adr/0005-portfolio-as-design-evidence.md)）。

## 4️⃣ aws-mondai をどうするか（お前の判断：非公開のまま）

**了解。非公開のままで問題ない。** 代わりにこう扱う：

| 場面 | どうするか |
|---|---|
| 職務経歴書 | プロジェクト概要と技術スタックを記載。**リポジトリURLは載せない** |
| 面接で聞かれたら | 「ソースは非公開ですが、よろしければ画面共有でデモをお見せします」 |
| なぜ非公開か聞かれたら | 「問題データの出典の扱いを整理できていないため、公開は保留しています」 |

**この答え方は加点になる。** 「著作権やデータの出典を気にする人」に見えるからだ。
むしろ無防備に公開している方がリスクだった。

> 💡 将来公開する場合は、ExamTopics由来の問題データを除いて
> 「アプリケーションのコードのみ」を公開する形にすればクリーンになる。
