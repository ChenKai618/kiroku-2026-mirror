# 前職の監視システム開発により、インフラ系タグの誠実性の懸念が解消された

[ADR-0004](./0004-target-by-visa-category.md) でクラウド／インフラ職を主戦場に定め、
スカウト媒体で「インフラエンジニア」「サーバーエンジニア」のタグを選択した。
だが**実務経験がないという誠実性の問題があり**、
「この欄はマッチング用のタグであって経歴の申告ではない」という
やや苦しい論理で正当化していた。

本人が後から提供した情報により、**この懸念は解消された。**

2019-2021年の案件は、単なる「C#/WPFの業務システム」ではなく
**複数サーバーホストの稼働監視・アラート通知システム**であった：

- 各ホストのCPU使用率・メモリ・ディスク空き容量を収集
- 閾値超過時のアラート通知
- システム間連携データの異常検知、ファイル生成間隔の監視
- WPF + Prism (MVVM) のクライアントと、ASP.NET Core + EF Core のAPIを一人で実装

**これは監視・運用（Observability）そのものであり、
CloudWatch や Zabbix が担う領域と同じである。**
つまりインフラ系タグは事実に裏付けられている。

## 守る線は変わらない

「監視システムを**作った**側であって、サーバーを**運用した**側ではない」
——この区別を面接で自分から述べる。
[ADR-0006](./0006-ai-assisted-development-disclosure.md) の原則の適用。

## 記載上の制約（守秘義務）

軍事関連の公的機関であるため、以下は書面にも口頭でも出さない：

- **データバス／総線のデータが何か** ← 書いた瞬間に用途（車両／艦船／航空）が推測される
- 監視対象サーバーが何をしていたか
- **「部隊」「軍」という語を書面に残す**（口頭で「国防関連の公的機関」と言えば足りる）
- 具体的な台数・閾値

**技術スタック（WPF・Prism・ASP.NET Core・EF Core）は一般技術であり記載可。**
**CPU・メモリ・ディスクの監視も、あらゆる監視システムが行うことであり記載可。**
**独自の業務ルールは抽象化する**
——「システム間連携データの異常検知」「ファイル生成間隔の監視」。

**能力を語り、対象を語らない。**

## 副次的な効果

この案件の実像が判明したことで、職務経歴の記述が全面的に強化された：

- 「C#/WPFの業務システム開発」→「監視システムのクライアント・API双方を一人で設計・実装」
- 技術スタックに **Prism (MVVM)・ASP.NET Core・EF Core** が追加され、
  アーキテクチャパターンとサーバーサイドの経験が可視化された
- 2019年時点で既に**フロント／バック双方を実装していた**ことになり、
  [ADR-0010](./0010-bridge-web-experience-gap.md) の技術線がさらに補強された

**本人が「部隊で作った小さなプログラム」と過小評価していたものが、
実際には職務経歴書で最も具体的に語れる案件の一つだった。**
