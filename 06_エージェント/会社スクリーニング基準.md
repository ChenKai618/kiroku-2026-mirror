## 0. この文書の目的

レバテック・ビズリーチ・求人票・ヘッドハンター提案の**会社をふるいにかける基準**。
**「この会社は良い会社か」ではなく「この会社に私は採用される可能性があるか」を判断する。**
金額・上場・条件の良さに惑わされない（過去2回、それで判断を誤った）。
**新規の会社・スカウトが来たときの流れ（4ステップ）**：
`1. 情報を取る（サイトの求人票／スカウト本文）→ 2. この文書で分析 → 3. ✅/⚠️/❌ を判定 → 4. 台账（求人台帳テンプレート.md）に1行記録`
調査の実行手順（何をどこで調べるか）は `求人スクリーニングプロンプト.md`。

## 2. 優先度順の会社タイプ

### 職種の現実（v3.1）：infraに「転向」はない

**「AWS/infraに転向したい」は誤ったフレーミング。** infra職は上流/下流に分かれており、
実務ゼロの人間が応募できるinfra求人は**ほぼ下流（監視・運用・障害対応）か派遣**に限られる。

| infraの層 | 内容 | 自動化の影響 | 実務ゼロで入れるか |
|---|---|---|---|
| 上流 | アーキテクチャ設計・移行計画・システム設計 | 弱（判断力が必要） | ❌ 実務必須 |
| 中流 | 構築・環境設定・IaC | 中 | ❌ ほぼ無理 |
| 下流 | 監視・運用・障害対応・夜勤 | **強（AI/自動化で縮小中）** | ✅ ここだけ |

- 求人票の「クラウドエンジニア」「インフラエンジニア」は**下流・派遣の言い換えであることが多い**
- ユーザーが望む「移行・設計・アーキテクチャ」は **infra側の入口ではなく、開発側の入口**にある
  （＝クラウド移行案件の開発・設計担当。現職と同型）
- **路線**：現職（移行案件の開発側）→ より良い移行/クラウド開発案件（本命）→ 2-3年後に内部で
  アーキテクト/infra上流へ。**今の職種転向は不要であり、むしろ遠回り**

### 全社を貫く選別キー（v3）：クラウド接触度

**職種名で分類しない。** 求人票の呼称（SE・SA・SRE・クラウドエンジニア等）は会社によって意味が違い、あてにならない。
どの会社でも次の順に確認する：

1. **構造的除外に当たらないか**（下記リスト）
2. **クラウド接触度**：入社後にAWS／クラウド案件に開発側で触れられるか
   - 高＝AWS移行・クラウドネイティブ案件を開発側で担当（現職と同型。理想）
   - 中＝自社SaaS等でクラウド基盤が身近（構成を理解する必要がある）
   - 低＝クラウドと無関係
3. **採用される可能性**（既存の3段階判定）

「高」は加点であって必須ではない。**最優先は安定（正社員・カテゴリー1/2）と年収**。
将来のクラウド転向は「入社後に実務を積んでから」の2年計画であり、今の職種転向ではない。

**第一優先（この中に本命がいる）**

1. **SIer／受託開発（中堅以上・プライム案件）**
   - 理由：現在の仕事と同一。**実務未経験の領域を証明する必要がない**
   - 例：ランドコンピュータ（東証プライム・Java・金融系）
2. **自社SaaS／自社サービス開発**
   - 理由：SESから完全脱却できる。育成枠（経験言語不問）があり、Javaが評価される
   - 例：ラクス（東証プライム・楽々シリーズ）
3. **事業会社の社内SE（開発系・インフラ系）**
   - 理由：上流中心・安定。大企業情シスはカテゴリー1/2で在留更新が楽

**第二優先（チャンスがあれば）**

4. **Web系・オープン系の開発職（クラウド含む）**
   - 理由：C#/Java/TS/Reactの経験が活きる。AWS職は「育成」なら応募可
   - ただし **AWS即戦力前提の求人は応募確率が低い**（挑戦枠）
   - 純クラウド職・SRE職の即戦力枠は**応募しない**（実務ゼロ）。**「育成枠」「ポテンシャル枠」「実務不問」の明記があるものだけ**挑戦枠に入れてよい

**ハード除外（何があっても応募しない）**

- ❌ **SES・派遣・客先常駐**（派遣形態は在留更新に追加書類が要る＋今と同じ問題を繰り返す）
  ※ これは**現在の除外**であり、絶対線ではない。**フォールバック発動条件**（＝第一波（本命+挑戦）を出して2〜3週間、
     書類通過0件 or 内定0のとき）を満たした場合のみ、最下段の最終フォールバックとして再評価する。
     選ぶ場合も実質年収350万以上・現職（300万）より確実に上 が条件。→ [ADR-0013](../docs/adr/0013-ses-exclusion-is-laddered-not-absolute.md)
- ❌ ヘルプデスク・テクニカルサポート・運用監視シフト（年収天井が低く、上流から遠い）
- ❌ PM/PL/アーキテクト/テックリード（経験不足）
- ❌ 英語必須（電話対応・ドキュメントが英語）
- ❌ クラウド実務経験が「必須」の求人（資格はあっても実務ゼロのため不合格になる）
- ❌ 生成AI特化・機械学習研究（要求水準が高い）

## 3. 許容範囲（第一次跳槽なので条件を緩める）

| 項目 | 許容する | 理由 |
|---|---|---|
| **上場/非上場** | 問わない（※ただし非上場でも中堅以上・安定経営が前提） | 第一次跳槽では上場は二次的。路は長い |
| **年収** | **400万〜が現実的レンジ**。450万目標・500万は順風・550万は撞大運 | 求人票の「想定年収」は宣伝。**実際に提示されるレンジで判断する** |
| **AWS未経験** | 許容（育成枠・ジュニア職なら応募可） | 資格は武器になるが、即戦力枠は無理 |
| **職種** | クラウド/インフラに限らない。**Web系・バックエンド・C#/Javaの開発職もOK** | codingの経験を活かす |
| **技術スタック** | Java・C#・TypeScript・React・Python いずれかが活きればOK | — |

**判断ライン（オファー受諾時・v3）**

**住居コストを織り込む**：現在は社宅2.5万/月（光熱別）。転居後は月5〜8万の民間賃貸を許容する。
→ 年収350万は家賃差分で現在と**実質横ばい**。ラインは400万で固定する。

```
400万以上   → 受諾検討（正社員・カテゴリー1/2が前提）
370〜400万  → 交渉必須。上流工程＋クラウド接触度が高い環境なら受諾も検討
350万前後   → 原則辞退。住居コスト込みで実質横ばい（現在+50万に見えて同じ問題）
350万未満   → 断る。契約更新 or 満了退社の方が正しい
```

## 4. 調査項目（会社ごとに必ず調べる）

### A. 事業形態（★最重要・最初に判断する）

| チェック | 判定 |
|---|---|
| 自社開発 / 受託 / SES / 派遣 / ハイブリッド のどれか | **SES・派遣は即除外** |
| 常駐か自社内勤務か | 「客先常駐」があれば派遣/SESの可能性が高い |
| 請け構造（元請/一次/二次/三次） | 二次請け以下は除外検討 |
| 主力顧客・主力案件 | 金融・公共・製造など |

**SES/派遣を見抜くサイン**：
- 求人票に「客先常駐」「派遣先で勤務」「プロジェクト型」「現場常駐」の文言
- 「所属」ではなく「参画」「アサイン」「待機」の語
- 雇用形態が「契約社員」「無期雇用派遣」
- 自社のサービス・プロダクトが無い

### B. 会社の基本情報

| 項目 | 調べ方 |
|---|---|
| 従業員数 | 会社HP・[企業分析.jp](https://kigyobunseki.jp/) |
| 設立年・資本金 | 会社HP・経済産業省 会社概要 |
| 決算・黒字か | 直近決算（黒字続きか） |
| 上場/非上場・市場 | 上場ならプライム/グロース/スタンダード |
| 事業内容・主力製品 | 会社HP・ニュース |

### C. 労働条件（求人票の「想定年収」を実質に読み替える）

| 項目 | 理由 |
|---|---|
| **固定残業代（みなし残業）の時間数** | 求人票の年収はこれ込みのことが多い。実質の基本給を計算する |
| 実際に提示されるレンジ | **「想定年収」は宣伝。「実際のレンジ」を面談で聞く** |
| 残業時間・休日 | 年休120日以上・残業20h以内が目安 |
| 賞与の月数 | 「業績により決定」は実質ゼロの可能性 |
| リモート | リモート可の企業は規模が大きく在留更新が楽 |

### D. 在留・外国人対応（二次的だが確認）

| 項目 | 理由 |
|---|---|
| 外国籍社員の在籍 | ビザ手続きに慣れているか |
| 在留更新を社内でやるか外部委託か | 外部委託の場合、行政書士が全書類を見る |

### E. 評判（口コミ・実態）

| ソース | 見る項目 |
|---|---|
| [OpenWork](https://www.openwork.jp/) | 年収・評価制度・残業・社風 |
| [転職会議](https://jobtalk.jp/) | 面接・選考体験 |
| [キャリコネ](https://careerconnection.jp/) | 年収・待遇 |
| [企業分析.jp](https://kigyobunseki.jp/) | 平均年収・勤続年数・決算 |

## 6. 応募の動かし方（v3.1）

### 応募配分（4層・合計100%）

**理想の序列**と**現実の配分**を分ける。第一志愿（自社SaaS/自社Web）は理想の頂点だが、**录用概率の主来源ではない**。投げる本数でバランスを取る：

| 層 | 配分 | 内容 | 位置づけ |
|---|---|---|---|
| **冲刺** | 20% | 自社SaaS・自社Web（Java/C#/全栈可：ラクス・ケアリッツ類）＋AWS育成枠 | **期望的第一志愿**。書類通過率は低いが、通れば理想。絶対に外さない |
| **主战场** | 35% | 一次受託・クラウド移行案件（ランド・AMBL・テノン・日立オープンポジション） | 现职的直接延伸。**拿offer的主来源**。クラウド接触度高 |
| **桥梁** | 30% | SIer・金融基幹（CAP等）＋云迁移相关 | 確実に内定を積む層。年収・安定を確保 |
| **保底** | 15% | フォールバック（タック类・条件明確なSES） | **11月中旬まで発動しない**。第一波の結果を見てから |

**数値の意味**：冲刺は「1〜2社だけ」ではなく**応募全体の20%（例：10社中2社）を割り当てる**。
理想だけ追うと全滅リスク、現実だけ追うと期望から遠ざかる——両方を同じ波で投げる。

- 応募は**台账の ✅判定から順に**行う。台账（サイト別）が入口、`応募管理表.md` が正式応募後の主表
- 第一波は **10〜15社**をこの4層に割り当てる。クラウド接触度と採用可能性で並べ、応募先の偏り（全部同じ業態等）をチェックする
- サイトでのエントリー操作は台账の状態を「応募依頼済」に。
  **猎头が処理して正式応募が成立した時点で応募管理表に1行追加**（重複応募チェックはここで行う）
- フォールバック（SES・派遣・客先常駐）は**この配分に含めない**。発動条件（第一波で2〜3週間、書類通過0件 or 内定0）を満たした場合のみ、別枠で再評価する

## 7. 新しい会話で会社を調査してもらうとき

**この文書を読ませた上で、こう頼む：**

```
「レバテックの求人リストを開いてください。
docs/06_エージェント/会社スクリーニング基準.md を読んで、
求人を A.事業形態→B.基本情報→C.労働条件→E.評判 の順で調べ、
各社を ✅応募 / ⚠️要確認 / ❌除外 に判定して、
応募構成（6章の10社）に当てはまる形でまとめてください。応募構成（v3・台账の✅判定）とクラウド接触度（高/中/低）を添えてまとめてください。

操作は読み取りのみ。応募・送信はしないでください。」
```

**調査の精度を上げるための注意**：
- 求人票の「想定年収」は信じず、**固定残業の時間数を必ず確認**
- SES/派遣のサイン（客先常駐・参画・アサイン・自社サービスなし）を必ずチェック
- 口コミ（OpenWork等）は年収と評価制度の実態確認に使う
- 判定は「この会社に採用される可能性」で行い、「会社の良さ」では行わない

## 8. 過去の判断の失敗（同じ轍を踏まないために）

| 失敗 | 内容 |
|---|---|
| 2026/8/29 スカウト分析 | 提示年収（400〜2000万）を自分の価値と誤読した。実は求人票の上下限だった |
| 2026/9/1 レバテック調査 | 6社全て「合格」＝会社の良さで判定。採用確率を見ていなかった |

**教訓**：**金額と条件の良さは、判断の材料にしない。** 判断するのは「この会社は自分を採用しそうか」。

- [ADR-0008](../docs/adr/0008-apply-before-ready.md)：準備完了を待たずに応募 → 応募10社を先行して回す
- [ADR-0008](../docs/adr/0008-apply-before-ready.md)：準備完了を待たずに応募 → 応募10社を先行して回す
- [ADR-0013](../docs/adr/0013-ses-exclusion-is-laddered-not-absolute.md)：SES/派遣の除外は絶対線でなく降級の最終段
- [ADR-0014](../docs/adr/0014-no-offer-exit-with-funds.md)：無内定でも満了退社は可能（資金・失業給付・2/28線）
