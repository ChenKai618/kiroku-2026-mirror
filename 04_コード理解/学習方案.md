# 自作コードを「面接で語れる」状態にする学習方案

> **前提の共有**：お前は「AIが書いたコードだから、まだ説明できない」と言った。それは正しい自己認識だ。
> だが状況はお前が思っているより**ずっと有利**だ。理由を先に言う。

## 🎯 この方案の核心：答えはもう書いてある

お前のリポジトリ `bikuri-NihongoLens` に、こういうファイルが入っている：

```

└── 0006-v1-scope-prototype-as-reference.md     (1,566 bytes)

```

**この6本のADRは、面接で聞かれる設計質問の答えそのものだ。**

例：俺が前回お前に出した「なぜダウンロードは並列で、文字起こしは直列なのか」という質問。
→ `0002-background-task-model.md` にこう書いてある：

> **並行策略**：**転録任務串行**（一次只跑一个）——单 GPU 同时转录会争抢显存、变慢甚至 OOM；
> **下载任务可并行**（网络受限，不争 GPU）。

**お前は答えを知っていた。読んでいなかっただけだ。**

しかも `0006` にはこう書いてある：「v1 范围以 **grilling 讨论** 为准」。
つまりお前は**過去にこのskillを使ってこのプロジェクトを設計している**。
設計判断はお前が下した。AIが書いたのは実装コードで、**判断はお前のものだ。**

### だからこの学習方案の目的は「勉強」ではない

**目的は「思い出す」ことだ。**

これは大きな違いだ。ゼロから理解するには数ヶ月かかるが、
自分が下した判断を思い出して言語化するのは、**1〜2週間で足りる。**

## Day 2〜3（各30分）— ADRを「面接の答え」に変換する

各ADRには必ず3つの要素がある：**決定・理由・却下した代替案**。
これは**そのまま面接の回答構造**だ。

### 変換テンプレート

```
面接官「なぜ○○という設計にしたのですか？」

あなた「【決定】○○という方針を採りました。
       【理由】というのは、△△という制約があったためです。
       【代替案】□□という選択肢も検討したのですが、
                ××という問題があったので見送りました。
       【結果】その代わり、◇◇という制約が残っています。」
```

**「却下した代替案を語れる」ことが、この構造の破壊力だ。**
なぜなら — **AIに書かせただけの人間は、却下した案を知らない。**
面接官が本当に見ているのは「考えた過程があるか」で、ADRはその証明そのものだ。

### ① ADR-0001 → 「なぜデスクトップアプリではなくローカルWebアプリにしたのか」

```
「ローカルWebアプリという構成を採りました。
localhostだけを listen するPythonバックエンドと、ブラウザで動くフロントエンドです。

理由は2つあります。
1つは、WhisperXとyt-dlpがどちらもPythonネイティブなので、
バックエンドがPythonなら自然に載るという点です。
もう1つは、字幕のタイムスタンプ同期とオートスクロールというUIが、
HTML5のvideo要素のtimeupdateイベントで実装するのが一番素直だった点です。

代替案としてPySide6の純デスクトップアプリも検討しました。
単一言語・単一プロセスでファイル処理は楽になるのですが、
字幕同期パネルと動画プレイヤーのUIコストが高く、
コーデック周りで踏む地雷も多いと判断して見送りました。

Electron + Pythonサイドカーも考えましたが、
IPCと重いパッケージングを個人利用のv1に持ち込むのは
オーバーエンジニアリングだと判断しました。

将来ネイティブアプリの見た目が必要になれば、
pywebviewやTauriで同じWeb UIをウィンドウに包めるので、
書き直しは発生しない設計にしています。」
```

**深掘り対策**：
- Q「なぜlocalhostだけ？」→ A「単人・単機・local-first が要件で、データを本機から出さない方針です」
- Q「セキュリティは？」→ A「外部公開しない前提なので認証は持たせていません。公開するなら設計を変える必要があります」

### ② ADR-0002 → 「なぜ文字起こしは直列で、ダウンロードは並列なのか」★最重要

```
「タスクを一等市民（first-class entity）としてモデリングしました。
各タスクはプロジェクトに属し、種別（ダウンロード/文字起こし）、
状態（待機・進行中・完了・失敗）、進捗を持ちます。

並行制御は、種別によって意図的に分けています。

文字起こしタスクは直列です。理由はGPUが1枚しかないためで、
同時に複数走らせるとVRAMを取り合って、遅くなるだけでなくOOMで落ちます。

一方でダウンロードタスクは並列で走らせています。
これはネットワーク律速でGPUを取り合わないためです。

つまり『ボトルネックとなるリソースが何か』でキューの方針を分けた、
というのが設計の要点です。

代替案として、タスクという実体を持たず
『処理中のプロジェクト』だけを表示する案も考えました。
実装は単純になりますが、タスク単位の進捗・リトライ・履歴の粒度が失われ、
『タスクパネル』という機能の意味自体がなくなるので採りませんでした。

なお、将来並列転録をしたくなった場合は、
先にVRAMのキューイングか隔離を解決する必要があります。
これはコードの表面を読んでも分からない制約なので、ADRに残してあります。」
```

**この最後の一段落が最強だ。**
「コードを読んでも分からない制約を文書に残した」＝**設計者の視点を持っている証拠**。
これを言える中途候補者は、日本で本当に少ない。

**深掘り対策**：
- Q「SSEを選んだ理由は？WebSocketではなく？」→ A「進捗配信は**サーバー→クライアントの一方向**で足りるので、双方向のWebSocketは不要でした。SSEはHTTPそのままで再接続も標準で入っています」
- Q「失敗時のリトライは？」→ A「失敗状態で止まり、リトライは新しいタスクを起こす形にしています。冪等性を保つためです」

---

### ③ ADR-0004 → 「再生時刻を唯一の状態源にした理由」★2番目に重要

```
「再生位置、つまり現在時刻を唯一の状態源（single source of truth）にしました。

同期が必要な表示面が3つあります。
左の単語ハイライト、右の字幕パネルの現在行ハイライトと自動スクロール、
下のタイムラインの再生ヘッドです。

これを全部、『現在時刻 + セグメント/単語のタイムスタンプ』から導出しています。
独立した『学習ポインタ』のような状態は持ちません。

だから『次へ/前へ』は隣の単語の開始位置にseekする操作になり、
単文ループはセグメントのendまで再生したらstartに戻す操作になります。
どの面をクリックしても、やることはseekです。

代替案として、再生から独立して動かせるポインタを持つ案を検討しました。
柔軟性は上がるのですが、
『再生時刻』と『ポインタ』という同期しうる状態が2つできてしまい、
実装が複雑になり、ズレのバグが出やすくなります。

実際、この手のUIで一番出やすいバグが『3つの表示がズレる』ことなので、
状態を1つにすることで構造的に排除しました。

トレードオフとして、将来『動画を止めたままハイライトだけ動かす』
書き取り練習のような機能を作る場合は、
既存のハイライトをこっそり切り離すのではなく、
明示的に別の状態を追加する必要があります。」
```

**「構造的に排除した」という表現を覚えろ。**
バグを「直した」のではなく「起こりえない設計にした」— これは設計思考の言語だ。

### ④ ADR-0003 → 「なぜSQLiteとファイルシステムを併用したのか」

```
「SQLiteとローカルライブラリフォルダのハイブリッド構成です。

SQLiteには構造化データを置いています。
プロジェクト、タスク、状態、メタ情報です。
これは複数のバックグラウンドタスクが並行して状態を書き換えるので、
トランザクションで壊れないようにする必要がありました。

一方、動画・音声・転録JSON・SRTといった大きなファイルは
ライブラリフォルダにプロジェクト単位で置き、DBからはパスで参照します。

セグメントと単語のデータは、v1では転録JSONの中に置いたままにして、
DBの行には展開していません。フロントが直接JSONを読んで描画します。
『プロジェクトをまたいで字幕検索』のような要件が出てきたときに
初めてインデックスを張ればいいと判断しました。

代替案として、DBを使わない純ファイル構成も検討しました。
一番シンプルで、フォルダごとコピーすれば移行できる利点がありますが、
プロジェクト一覧とタスク状態をフォルダスキャンで作る必要があり、
並行してmeta.jsonを書くと壊れるリスクがあるので採りませんでした。」
```

**深掘り対策**：
- Q「なぜPostgreSQLではなく？」→ A「単機・単人利用でサーバープロセスを増やしたくなかったためです。DBがファイル1つで済むので、ライブラリフォルダごとバックアップできます」
- Q「JSONをDBに入れないのは正規化として問題ないか？」→ A「意図的です。v1では読み取り専用の塊なので、YAGNIの判断をしました。検索要件が出たらインデックスを張ります」

## 🚨 「AIで作った」と聞かれたときの答え（必ず準備しろ）

2026年、日本の面接官もAI生成ポートフォリオを警戒し始めている。
**隠すな。隠すと嘘になり、嘘は崩れる。正面から答える方が強い。**

```
面接官「これはAIを使って開発されたものですか？」

あなた「はい、実装には生成AIを積極的に使っています。

ただ、AIに任せているのは実装で、設計判断は自分でしています。
たとえばこのプロジェクトでは、
アーキテクチャの決定を6本のADRとして文書化しているのですが、
『GPUが1枚なので文字起こしは直列にする』
『再生時刻を唯一の状態源にして表示面の同期バグを構造的に防ぐ』
といった判断の理由と、却下した代替案を全部残しています。

AIを使うほど、逆に『何を作るか』『なぜそうするか』を
自分で決めて言語化する必要が出てくる、というのが実感です。
指示が曖昧だと、動くけれど後で崩れるコードが出てくるので。

実務でもAIを使う前提の開発になっていくと思うので、
その使い方を個人開発で練習している、という位置づけです。」
```

**なぜこれが効くか**：
- 隠さないので、後から矛盾しない
- **「AIを使うほど設計力が要る」という主張は、2026年の実務認識として正しい**
- ADRという物証がある
- 「実務でもそうなる」＝入社後の働き方の話に転換できている
