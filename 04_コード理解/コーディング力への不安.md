> **結論を先に：お前が怖がっているものは、お前が受ける会社にはほとんど存在しない。**
> そして「久しく코ードを触っていない」という自己認識は、データ上、事実ではない。

## 1️⃣ まず事実確認：お前は「久しくコードを触っていない」のか

GitHub のコミット履歴を実際に数えた。

```

2026-08   bikuri-goizukan     11 commits

半年で 200コミット超・4プロジェクト・2件を公開稼働
```

**これは「久しく触っていない」ではない。高強度の開発期だ。**

しかもこの半年、お前は同時に：
- 中国から日本に移住した
- 初めての日本の現場に入った
- AWS を1ヶ月で3つ取った

**この状態で200コミットしている人間を、「コードから離れている」とは言わない。**

### では、本当の問題は何か

お前が感じている不安は、実は**別のもの**だ：

| お前が言っていること | 実際の状態 |
|---|---|
| 「久しくコードを触っていない」 | ❌ 事実ではない。半年で200コミット |
| 「AIで開発している」 | ✅ 事実。だがそれ自体は問題ではない |
| **「AIを切ったとき、指が動くか自信がない」** | ✅ **これが本当の不安。そしてこれだけが本当の課題** |

**設計はできる。デバッグもできる。システムも読める。**
**不確かなのは「補完なしで手が動くか」という、筋肉記憶の部分だけだ。**

そして筋肉記憶は、**エンジニアリング能力の中で最も回復しやすい**。
学び直す必要はなく、神経回路を通し直すだけ。**3週間・1日30分で戻る。**

本当に回復しづらいのは設計判断力とシステム勘の方で、**それはお前が持っている**。
証拠がADR 6本だ。

> **お前は、最も補いやすい欠点を、最も根本的な欠陥だと誤認している。**

## 2️⃣ アルゴリズムテストは、お前が受ける会社にほぼ存在しない

これが最も重要な事実だ。

### お前の応募先（Q12で確定済み）と、実際の技術選考の形

| 応募先 | 配分 | 技術選考の実際の形 |
|---|---|---|
| **クラウド/インフラ職** | **6社（40%）** | AWS構成の口頭質問・アーキテクチャ図の議論。**アルゴリズムではない** |
| **SIer / 元請け** | 4社（27%） | コーディングテストは稀。**設計書が書けるか・工程を回せるか** |
| **事業会社の社内SE** | 3社（20%） | ほぼなし。**業務部門との対話・上流理解** |
| 自社開発 / Web系 | **2社（13%）** | ← **アルゴリズム系はここに集中している** |

**お前は13%のリスクを、100%の関門として恐れている。**

### そして、その2社ですら

日本の自社開発企業のコーディングテストは、米国のような
「LeetCode Hard を45分」型は**少数派**だ。多いのは：

| 形式 | 内容 | お前の適性 |
|---|---|---|
| **持ち帰り課題** | 「簡単なWeb APIを作って提出」（数日の猶予） | ✅ **むしろ得意分野**。お前は完成させてデプロイまでやる人間だ |
| **ペアプロ形式** | 面接官と一緒に小さな機能を実装 | ⚠️ 手が止まると見える。要練習 |
| **既存コードのレビュー** | 「このコードの問題点を指摘して」 | ✅ **強い**。ADRを書ける人間はレビューができる |
| **設計課題** | 「こういうサービスをどう設計する？」 | ✅ **最も強い**。ADRそのものだ |
| ライブコーディング（アルゴリズム） | FizzBuzz〜簡単なデータ構造 | ⚠️ **これだけが弱点。だが3週間で戻る** |

### クラウド職の面接で実際に聞かれること

```
「オンプレからAWSに移行するとき、まず何を考えますか」
「EC2とコンテナ、どう選び分けますか」
「マルチAZ構成にする理由は」
「移行時にデータの整合性をどう担保しますか」
「コスト最適化で最初に見るところは」
```

**これらは全部、お前が SAP の学習で通った内容で、しかも現在の現場で見ている光景だ。**

**アルゴリズムを聞かれる場所を避けて、自分の弾薬が効く場所を選ぶ。**
これは逃げではなく、**戦術**だ。応募先の選定はすでにそう設計してある。

## 3️⃣ 3週間 無AI回復トレーニング（1日30分）

**目的は「アルゴリズムが得意になること」ではない。**
**「AIなしで手が止まらない」状態を取り戻すこと。それだけ。**

### ルール

```
・エディタの AI 補完を完全にOFF（Copilot / Cursor の Tab を切る）
・ChatGPT / Claude を開かない
・公式ドキュメントと MDN は見てよい（実務でも見る）
・30分でできなくても、時間が来たら終わる
・終わったら AI に見せて講評をもらう ← ここで学ぶ
```

**最後の項目が重要。** AIを禁止するのではなく、**書いた後に使う**。
順番を変えるだけで、AIは松葉杖から教師に変わる。

### Week 1：手を動かす感覚を戻す（易しいものを速く）

言語は **TypeScript**（お前のメイン）。paiza や AtCoder Beginner の A・B 問題でよい。

| 日 | お題 | 確認すること |
|---|---|---|
| 1 | FizzBuzz を3通りの書き方で | 手が動くか。それだけ |
| 2 | 配列から重複を除く（Set を使う版／使わない版） | Set・Map が手癖で出るか |
| 3 | 文字列の反転・回文判定 | 文字列APIを覚えているか |
| 4 | オブジェクトの配列を特定キーでグループ化 | `reduce` が書けるか ★実務で最頻出 |
| 5 | 配列のソート（数値・文字列・オブジェクトのキー） | `sort` の比較関数を覚えているか |
| 6 | フィボナッチ（再帰／ループ／メモ化） | 再帰の書き方。**メモ化＝DPの入り口** |
| 7 | 復習。1〜6で詰まったものだけ |  |

### Week 2：実務に近い形（ここが本命）

| 日 | お題 | なぜこれか |
|---|---|---|
| 8 | fetch でAPIを叩き、結果を型付きで整形 | **実務そのもの** |
| 9 | try-catch とエラー型の設計 | 「エラーハンドリングどうしてる？」の答えになる |
| 10 | Promise.all / 直列実行の書き分け | ★**ADR-0002 の並列/直列の話とコードで繋がる** |

| 12 | 配列操作の連鎖（filter → map → reduce） | JS/TSの中核 |
| 13 | 小さな関数にユニットテストを書く（Vitest / Jest） | ★**「テスト書いてる？」に答えられる** |
| 14 | 復習 |  |

### Week 3：自分のコードで実践（最も価値が高い）

**ここが本当の目的地だ。** 新しい問題を解くのではなく、**自分のリポジトリに手を入れる**。

| 日 | お題 |
|---|---|
| 15-16 | `bikuri-goizukan` に小さな機能を**AIなしで**追加（検索ボックス等） |

**Week 3 が終わったとき、お前は面接でこう言える**：

```
「直近では、自分の個人開発プロジェクトに機能を追加しています。
たとえば○○という機能を実装したときは、△△という点で悩みました。」
```

**これは「AIで作りました」より圧倒的に強い。**
そして**嘘ではない。実際にやったことになる。**

## 4️⃣ コーディングテストで詰まったときの台本

**詰まること自体は減点ではない。詰まり方が評価される。**

日本の面接官が実際に見ているのは、正解にたどり着いたかではなく：
- 考えていることを口に出せるか
- 詰まったとき、何をするか
- 質問できるか
- 部分点を取りに行けるか

### 台本①：問題を受け取った直後（必ずこれをやれ）

```
「まず確認させてください。
入力は○○という前提でよろしいでしょうか。
空の場合や、想定外の値が来た場合の扱いはどうしましょうか。」
```

**いきなり書き始めるな。** 要件確認をする候補者は、それだけで評価が上がる。
**そして考える時間が稼げる。**

### 台本②：解法を思いついたら、書く前に宣言する

```
「まず一番素直な方法で書いてみます。
おそらく計算量はO(n²)になりますが、
まず動くものを作ってから改善したいと思います。」
```

**「まず動かす、次に改善」は実務の正しい順序だ。**
これを言えるだけで「実務ができる人」に見える。

### 台本③：手が止まったとき（最重要）

**沈黙が最悪。何を考えているかを実況しろ。**

```
「すみません、少し考えさせてください。

今、○○という方法を考えているのですが、
△△のケースで破綻しそうな気がしています。

一度、別のアプローチを試してもよろしいでしょうか。」
```

### 台本④：本当に分からないとき

```
「申し訳ありません、この場では解法が浮かびません。

ただ、実務であれば、
まず似た処理が既存コードにないか探して、
なければドキュメントや資料を調べて実装します。

考え方の方向だけでもヒントをいただけますでしょうか。」
```

**ヒントを求めるのは減点ではない。** 多くの面接官はヒントを出す準備をしている。
**黙り込むのが最悪の対応だ。**

### 台本⑤：終わった後

```
「今回は時間内に完成しませんでしたが、
帰ってから解き直して、
もしよろしければ結果をお送りしてもよろしいでしょうか。」
```

**これを実際にやると、印象が逆転することがある。**

## 5️⃣ 「AIで書いている」ことへの不安について

### 誠実に見て、お前の状態はこうだ

| 項目 | 実際 |
|---|---|
| AIなしでゼロから大規模実装 | ⚠️ 現状は難しい |
| AIなしで既存コードを読む | ✅ できる（訓練中） |
| AIなしで小さな修正 | ⚠️ **3週間で戻る（上の訓練）** |
| **何を作るか決める** | ✅ **できる。ADRが証拠** |
| **なぜそうするか説明する** | ✅ **できる。ADRが証拠** |
| **AIの出力が正しいか判断する** | ⚠️ ここが本当に鍛えるべき所 |
| デバッグ・原因調査 | ✅ できる（プロジェクトが動いている以上） |

**設計判断ができて実装が弱い人間**は、市場では**実装が速くて設計ができない人間**より価値が高い。
後者はAIで代替できるが、前者はできない。

### そして最も重要なこと

**俺たちが作った資料には、嘘が一つもない。**

- 職務経歴書：全部事実（架空の会社を作らなかった）
- 「AIで作ったか」→ **自分から「使っています」と言う**
- 「AWS実務は？」→ **自分から「まだ浅い」と言う**
- 2019-2021 → 実在の「公的機関」

**インポスター症候群の解毒剤は、詐称しないことだ。**

お前が恐れている「入社後にバレる」というシナリオには、
**バレるべき嘘が存在しない。**

企業が知った上で採用するなら、それは企業の判断だ。
**お前が代わりに自分を落とす必要はない。**

## 6️⃣ 応募の判断基準（自己否決の禁止）

**恐怖は応募の判断に参加させない。** 判断基準はこれだけ：

### ✅ 迷わず応募する
- クラウド / インフラ / AWS 関連
- SIer・受託の Java / 業務システム
- 事業会社の社内SE
- 要件の**50〜70%**を満たしている
- 足りないのが**特定のフレームワーク**や**実務年数**

### ⚠️ とりあえず応募する（判断は企業に任せる）
- 経験年数が1〜2年足りない
- 技術スタックが一部違う
- 「実務経験3年以上」と書いてある（**日本の求人票の年数は努力目標であることが多い**）
- コーディングテストの内容が不明

### ❌ 戦略的に見送る（**ここだけは自分で決めてよい**）
- 機械学習の論文・研究が必須
- 競技プログラミングの実績を明示的に要求
- モデルをゼロから学習させる仕事
- 数学モデリングが中核
- **そもそもやりたくない仕事**

**自分から落とすのは3番目だけ。** 1番と2番は企業に判断させろ。

## 7️⃣ 最低ライン（これを満たせば応募してよい）

「100%の能力」は不要。この線を超えていれば十分だ：

- [ ] 自分のプロジェクトの主要なコードを読んで説明できる
- [ ] AIなしで小さなTypeScriptの修正ができる（**3週間の訓練で到達**）
- [ ] エラースタックを読んで原因の見当がつく
- [ ] Git の基本操作（branch / merge / rebase / conflict解決）
- [ ] API・DB・認証の流れを説明できる
- [ ] AI生成コードをレビューして問題を指摘できる
- [ ] 機能にテストを追加できる
- [ ] **実際の失敗と修復の経験を1つ語れる**
- [ ] 分からないことを整理して質問できる
- [ ] 1〜2時間進捗がないとき、自分から報告できる

**最後の2つが、実務で最も評価される。** そしてこれは技術力ではない。

## 8️⃣ 恐怖を消してから動くな

お前は、こうなる可能性が高い：

```
応募するとき      → 怖い
面接に呼ばれたとき → 後悔する
面接の前          → 自分は無理だと思う
面接の後          → 答えられなかった所を反芻する
内定が出たとき    → 相手が誤判したのではと疑う
入社の前          → バレるのではと恐れる
入社1週目        → 全員が自分より優秀に見える
```

**これは失敗のサインではない。全部、正常な過程だ。**

「不安がなくなってから応募する」というルールを採用すると、
**不安に拒否権を与えることになる。**

正しいルールはこれだ：

```
┌────────────────────────────────────────┐
│  不安は感じてよい。                       │
│  だが、応募の判断には参加させない。         │
└────────────────────────────────────────┘
```

## 9️⃣ 実際にやること（今週から）

| いつ | 何を |
|---|---|
| **今週** | 応募を開始する。**訓練の完了を待たない** |
| **今週から毎日30分** | 無AI訓練 Week 1（`①`のリスト） |
| 書類選考期（1〜2週間） | 技術は聞かれない。**この期間に訓練が進む** |
| 3週間後 | 訓練完了。ちょうど技術面接が始まる頃 |

**タイミングは既に合っている。**
書類選考に1〜2週間、一次面接まで3〜4週間。**訓練が終わる頃に、技術面接が来る。**

**「準備してから応募」ではなく「応募しながら準備」が、時間軸的にも正しい。**

## 🔟 校正は、頭の中ではなく市場でやれ

自分の市場価値は、家では絶対に分からない。

```
5社応募   → 書類が通るか見る
3社面接   → 何を追及されるか記録する
1-2社テスト → 実際の難易度を知る
2週間補強 → 次のバッチへ
```

- 書類が全く通らない → 履歴書の問題。エージェントに添削させろ
- 面接でプロジェクト説明に詰まる → コード理解を強化
- 基礎コーディングで落ちる → 無AI訓練を延長
- **そもそもアルゴリズムを聞かれない** → **恐怖の対象が存在しなかったと判明する**

**最後のパターンになる確率が、お前の応募先構成では最も高い。**

頭の中で100回シミュレーションするより、**1回の実際の面接の方が正確な情報をくれる。**
